Start with one VM

Install skiff, start a Linux VM on your Mac, reach it over SSH and bring its ports to localhost.

Install

skiff needs Apple Silicon, macOS 26 or newer (what Apple's container supports), and Homebrew. Check a Mac with skiff doctor.

$ brew install sovyn-eu/tap/skiff
$ skiff prepare

With Go 1.26+ you can build it instead: go install github.com/sovyn-eu/skiff/cmd/skiff@latest.

prepare is a one-time setup of about a minute and safe to run again. It installs Apple's container through Homebrew if needed, starts its service, builds the guest image (Ubuntu 24.04 with systemd, sshd, your key and an internet-only firewall) and writes an SSH key pair to ~/.skiff.

Create and connect

$ skiff new dev 
dev is running at 192.168.64.2
  skiff ssh dev
  ssh dev.skiff

new boots a fresh Ubuntu 24.04 in about half a second and returns once it answers SSH, about two seconds after you hit enter. Without a name, VMs are called vm1, vm2 and so on.

$ skiff ssh dev

You are root in an Ubuntu 24.04 with its own kernel, disk and IP. To use plain ssh, scp, rsync or your IDE, add one line to ~/.ssh/config:

+ Include ~/.skiff/ssh_config

Then ssh dev.skiff works from anywhere. skiff's ProxyCommand connects to the VM and verifies the host key pinned at creation, so neither port forwarding nor sudo is needed on macOS.

Size

Defaults are 2 vCPUs and 1 GiB RAM, the minimum Apple's container accepts. The disk is a sparse volume that grows as the VM writes, so there is nothing to size there.

$ skiff new dev --vcpus 4 --mem 2048

The guest is a plain Ubuntu 24.04 with git, curl and jq. Install what a task needs over SSH; the agent guide shows the commands for Node, Claude Code and gh.

Forward ports

Guest ports appear as localhost:PORT on the Mac. Forwards survive stop and start and go away with the VM. Host ports must be 1024 or higher.

$ skiff new web -p 8080:80 -p 3000
$ skiff forward web 5432

skiff forward web without ports lists them; skiff unforward web 5432 removes one.

Profiles: what a VM needs

Instead of installing by hand after every new, describe what a VM needs in a profile: its size, the capabilities to grant, packages, agent CLIs and skills to install, and the plugins, MCP servers and settings of Claude Code or Codex inside. A .skiff file in a repository holds what that repository needs; ~/.skiff/profile.toml is the machine default for every VM. skiff new merges both, flags win.

$ skiff profile init 
grants = ["claude", "github"]
skills = ["anthropics/skills/skills/pdf"]

[machine]
vcpus = 4
mem = 4096

[guest]
tools = ["claude"]
packages = ["nodejs", "npm"]

[claude]
plugins = ["frontend-design@claude-plugins-official"]
[claude.mcp.context7]
type = "http"
url = "https://mcp.context7.com/mcp"
$ skiff profile trust && skiff new agent1

The VM boots, the setup runs as root (packages, tools, skills, then your setup script) with its output on your terminal, the grants are made and the agent configuration is written. skiff profile show --render shows exactly what the guest will get. On an M4 Pro, a VM with Claude Code, Codex and a skill is ready in about 50 seconds.

Trusting a repository's .skiff

A .skiff is as trustworthy as its repository: it chooses grants, forwards host ports and runs a script as root in the VM, and the grants apply to whatever runs in the VM afterwards. So new and apply refuse a repository file until you have trusted it, and the refusal says what the file would do:

skiff: profile is not trusted: .skiff (it grants claude, github, forwards ports 3000,
runs a setup as root in the VM, configures the agents); read it with
'skiff profile show --render', then 'skiff profile trust' or --trust, or pass --no-profile

skiff profile trust records the file's SHA-256 and path in ~/.skiff/trusted, like direnv's allow; an edit needs a new trust. --trust on new or apply does it in the same run, --no-profile ignores the repository file. Your own ~/.skiff/profile.toml needs no trust.

Limiting what a repository may grant

Trust says you have read a file. To cap what any repository file may ask for, however often you trust it, list the allowed grants in your machine default:

# ~/.skiff/profile.toml
grants = ["claude"]
allow_grants = ["claude", "github"]

A .skiff or --profile file that asks for anything else, such as ssh-agent, is refused before the trust check, so --trust does not lift it. allow_grants = [] lets no repository file grant anything; without the key there is no limit. Your own --grant, skiff grant and the default's own grants are not limited, and a repository file cannot set allow_grants itself.

Keeping a VM up to date

$ skiff apply agent1

apply brings a running VM to the state of the profile after you edited it: grants the profile lists are added, the agent configuration is rewritten and what the old profile wrote and the new one no longer names is removed. The setup does not run again unless you pass --setup, which reinstalls packages, tools and skills and runs your script once more; close the VM's sessions and tunnels first, because the setup must see neither the broker nor a forwarded SSH agent. Grants are only ever added; withdraw one with skiff revoke.

Change in .skiffCommand
plugin, MCP server, setting or grant addedskiff apply agent1
package, tool or skill added or changedskiff apply agent1 --setup
grant removedskiff revoke agent1 CAP
profile dropped altogetherskiff apply agent1 --clear

Plugins from a marketplace the profile declares itself install on the second Claude Code session: the first registers the marketplace, the next installs from it. Plugins from claude-plugins-official install on the first.

The README has the full file format and what lands where in the guest.

What a VM can reach

The internet, through NAT, and nothing else: a firewall in the guest rejects your Mac, your LAN and other VMs. Root in the VM can lift it, so treat it as a guard rail. The only controlled way back to the Mac is the capability broker.

Troubleshooting

  • Exit code 255 from ssh or exec means the connection failed; check skiff ls.
  • After a reboot of the Mac, the next skiff command starts the container service and the VMs that were running come back; ones stopped with skiff stop stay stopped. If one fails to boot, skiff start NAME retries it.
  • broken in skiff ls means damaged metadata; skiff rm NAME cleans it up.
  • Boot log of a VM: container machine logs NAME; port forwards: ~/.skiff/relay.log
  • Reset everything: skiff rm each VM, then rm -rf ~/.skiff

Before you leave

$ skiff stop dev

Stop keeps the disk; rm is a separate step.
